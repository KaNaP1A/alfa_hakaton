оценка качества рекомендаций или нагрузочное тестирование.

## Исправления

`model_runtime.py` раньше применял `Path.resolve()` к Python виртуального окружения.
На macOS это раскрывает символическую ссылку до системного Python и теряет зависимости:
запуск падал с `ModuleNotFoundError: No module named 'alfa_reco'`.
Теперь путь остаётся внутри venv; все дочерние процессы получают `PYTHONPATH` текущего
checkout и `HF_HUB_OFFLINE=1`. Регрессионный тест проверяет реальный `sys.prefix`
и путь импортированного модуля в отдельном venv.

Старый тест реальной модели импортировал лишь несколько карточек и проверял HTTP 200
для рекомендаций/плана. Он мог пропустить пустую выдачу из-за отсутствия карточек
в бэкенде. Теперь тест использует полный тестовый каталог и проверяет содержимое.
Для плана выбрана история по налогам с тематическим продолжением: у произвольного курса
может законно не быть достаточно связанных материалов (`insufficient_evidence`).

## Повторный запуск

Зависимости бэкенда устанавливаются отдельно: из `backend` выполнить
`uv sync --frozen --extra dev`. Python алгоритма должен иметь зависимости
`05_code/requirements-relevance.txt`; уже подготовленное окружение можно использовать повторно.

Первый терминал, из корня репозитория, с новым каталогом runtime:

```bash
python3 backend/scripts/model_runtime.py \
  --bundle /абсолютный/путь/к/исходному-комплекту \
  --runtime models/runtime \
  --python /абсолютный/путь/к/окружению-модели/bin/python \
  --port 18000
```

Скрипт проверяет и копирует комплект; отказывается перезаписывать существующий runtime.
Для последующих запусков этой готовой копии, также из корня:

```bash
PYTHONPATH=05_code/src HF_HUB_OFFLINE=1 \
  /абсолютный/путь/к/окружению-модели/bin/python -m alfa_reco serve \
  --output models/runtime/catalog --relevance --no-llm --port 18000
```

Второй терминал, из `backend`, **однократно** создать отдельную базу для проверки:

```bash
.venv/bin/python scripts/seed_model_sandbox.py \
  --catalog ../models/runtime/catalog \
  --database ../models/sandbox/backend.sqlite3
```

Этот скрипт задаёт искусственные `published=true`, `access=public` только в новой
тестовой SQLite-базе. Он не переносит цены и ссылки и отказывается перезаписывать базу.
Не использовать эту базу для реальных пользователей. Исходный комплект остаётся неизменным.
Для настоящего каталога сайта вместо этого используется `alfa-backend import-catalog`.

Запустить API из того же `backend`:

```bash
ALFA_DATABASE_URL=sqlite:///../models/sandbox/backend.sqlite3 \
ALFA_RECO_MODE=http ALFA_RECO_URL=http://127.0.0.1:18000 ALFA_RECO_TIMEOUT=120 \
  .venv/bin/python -m uvicorn app:create_app --factory \
  --host 127.0.0.1 --port 8080 --no-access-log --no-proxy-headers
```

Swagger: <http://127.0.0.1:8080/docs>. Регистрация и Authorize описаны в README.
Для этой рабочей копии окружение алгоритма находится по пути `05_code/.venv/bin/python`
от корня `integrated`; runtime и тестовая база уже подготовлены.

Третий терминал, из `backend`:

```bash
.venv/bin/python examples/smoke_real.py http://127.0.0.1:8080

ALFA_REAL_RECO_URL=http://127.0.0.1:18000 ALFA_REAL_BUNDLE=../models/runtime \
  .venv/bin/python -m unittest discover -s tests -v

.venv/bin/mypy
.venv/bin/ruff check .
.venv/bin/ruff format --check .
```

HTTP smoke создаёт отдельного временного пользователя, записывает одно событие и отзывает
его токен. Учётная запись остаётся в тестовой базе. Вывод не содержит токенов/паролей;
локальный результат этой проверки сохранён в `models/sandbox/smoke-report.json`.
Остановка сервисов — Ctrl+C в каждом из двух терминалов.

## Что эта проверка не подтверждает

Использованы реальные модель и метаданные снимка, но **права и публикация в тестовой базе
искусственные**, цены и ссылки неизвестны. Для рабочего окружения нужен актуальный
доверенный импорт сайта. Docker и PostgreSQL в этом прогоне не проверялись.
Расширенные поля профиля сохраняются бэкендом, но внутренний `/recommend` пока получает
только категории и историю; это ограничение текущего контракта.
