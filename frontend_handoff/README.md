# Инструкция для фронтендера: поиск, рекомендации и учебный маршрут

Пакет содержит отдельный локальный стенд на вымышленных данных. Он нужен для разработки интерфейса, когда реальный бэкенд или модель ещё недоступны. Стенд не ищет по каталогу, не ранжирует материалы, не проверяет права и не моделирует покупку. Все названия, ID и тексты вымышлены. Файлы стенда можно передать фронтендеру отдельно; реальные каталоги и модели не нужны. Ссылки на общие документы проекта работают только внутри полной рабочей копии; для стенда достаточно этой инструкции.

## 1. Быстрый старт без установки зависимостей

Нужен Python 3.10 или новее. В терминале перейдите в папку `frontend_handoff` и запустите:

```bash
python3 mock_server.py
```

Откройте **http://127.0.0.1:8765/**. Страница демонстрирует запрос и вывод фиктивных карточек. Введите «пусто» или «уточнение», чтобы увидеть состояние без результатов. Остановить сервер — `Ctrl+C`. Если порт занят:

```bash
python3 mock_server.py --port 8766
```

Используйте адрес с новым портом. Страница и API раздаются одним сервером: дополнительные CORS-настройки не нужны. Непосредственное открытие `index.html` как файла не подключит API. Стенд слушает только `127.0.0.1`; это не сервер для продакшена. Никакой Node.js, Docker, модели, ключей и каталога для него не нужно.

### Состав пакета

- `mock_server.py` — фиксированные учебные ответы для `/health`, `/suggest`, `/search`, `/catalog`, `/recommend` и `/development-plan`.
- `index.html`, `app.js` — минимальный пример `fetch` и безопасного текстового отображения ответа; это не дизайн итогового сайта.
- Эта инструкция — какие состояния нужны интерфейсу и что уже поддерживает существующий прототип.

## 2. Как соединяются части проекта

```text
Браузер / фронтенд → API бэкенда сайта → рекомендательный алгоритм
                                  ↘ актуальный каталог, доступ, цены, прогресс
```

Браузер в продукте обращается к бэкенду сайта; адреса его публичного API, авторизацию и точную схему ответа необходимо согласовать с бэкендером. Примеры ниже описывают **внутренний локальный прототип алгоритма**, а не уже существующие публичные адреса бэкенда. Не открывайте порт алгоритма напрямую в интернет. Локальный сервер алгоритма не поддерживает произвольный cross-origin доступ; для разработки отдельных серверов бэкендер может настроить same-origin proxy, согласовав `Host`/`Origin` с ограничениями прототипа. Мок включён только для визуальной разработки.

Бэкенд проверяет актуальную публикацию, наличие и права пользователя, сопоставляет ID с каталогом, предоставляет подтверждённые ссылки, условия доступа и цену, хранит историю и прогресс. Алгоритм возвращает порядок и объяснения по снимку. Снимок не подтверждает реальную цену, ссылку и право доступа. Фронтенд не должен самостоятельно делать такую проверку и считать её защитой.

## 3. Что можно показывать уже сейчас

| Сценарий | Что поддерживает прототип алгоритма | Состояния интерфейса |
|---|---|---|
| Поиск по задаче | `GET /search`; готовые `results` и отдельно `alternatives` | загрузка, результаты, пустой ответ, ошибка; уточнение может быть и при наличии результатов |
| Подсказки при вводе | `GET /suggest` | нет подсказок, список `completions` и `related_topics`, выбор варианта |
| Рекомендации по интересам | `POST /recommend`: категории и просмотренные материалы | список или отсутствие рекомендаций; просмотр не означает завершение |
| План по истории | `POST /development-plan`: просмотры и завершённые курсы; до 3 шагов | `needs_activity`, `insufficient_evidence`, `partial`, `ready`; возможен короткий маршрут |
| Карточки | название, тип, описание, `promotion.text`, иногда `reason` | длинные и отсутствующие поля, неподтверждённая цена/ссылка, отсутствие доступа |

**Пока не реализованы в действующем HTTP API:** фильтр только платных предложений, коммерческое ранжирование с учётом цены, подтверждённые покупки и подписки, продолжение курса по фактическому прогрессу, отдельный продаваемый урок и полноценный персональный учебный маршрут. Не отображайте их как работающие функции. Предложение курса после обучения сейчас — тематическая эвристика, а не доказанный порядок предпосылок.

Типы: `course` — курс, `article` — статья, `document` — документ, `webinar` — вебинар, `podcast` — подкаст, `calculator` — калькулятор. Отдельного пользовательского типа `lesson` пока нет. Путь обучения и коммерческая политика описаны в [плане проекта](../docs/ПЛАН_ПРОДАЖИ_И_УДЕРЖАНИЕ.md) — это план, а не текущий API.

## 4. Как читать ответы

1. Сохраняйте порядок массива `results` и массива `steps`. `scores.final_score` не является вероятностью; пересортировка по нему может изменить корректный порядок.
2. Для связи результата с каталогом используйте `entity_key` и `generation`. ID из старой версии каталога могут быть отклонены: при смене `generation` обновите данные через бэкенд. Мок использует только `mock-generation-1`.
3. `promotion.text` — короткое обоснование по снимку; оно не доказывает наличие товара, цены или персональную выгоду. Право его показа и актуальность текста проверяет бэкенд. Привлекательное описание не должно придумывать скидку, гарантию или результат обучения.
4. `price.status`, `access_type`, `canonical_url` из результата алгоритма — сведения снимка; актуальные цену, валюту, кнопку перехода и доступ показывайте по подтверждённым данным бэкенда. `unknown` не значит «бесплатно». Не стройте URL из ID самостоятельно.
5. `alternatives` не смешивайте с основными результатами как равнозначные — это частичные альтернативы. Бэкенд проверяет доступ и к ним. Если список пуст, не создавайте случайные результаты для заполнения экрана.
6. План может вернуть `notice` и `steps: []`. При удалении шага бэкендом из-за прав целостность оставшегося маршрута нужно проверять: нельзя обещать, что он остался прежним. Шаг содержит `number`, `title`, `material`, `why`, `action`, `order_reason`, `evidence`.
7. Показывайте данные как текст, а не доверенный HTML. Обрабатывайте отсутствующие необязательные поля, 400, 404, 500, сетевые ошибки и таймауты. Учтите клавиатурную навигацию и доступные подписи.

## 5. Примеры запросов к локальному стенду

Примеры выполняются в другом окне терминала после запуска сервера. Любой непустой запрос, кроме специальных сценариев ниже, возвращает одни и те же фиктивные карточки — это **не** качество поиска.

```bash
curl -s http://127.0.0.1:8765/health
```

```bash
curl -sG http://127.0.0.1:8765/search --data-urlencode 'q=Управление командой' --data 'mode=relevance'
```

```bash
curl -sG http://127.0.0.1:8765/search --data-urlencode 'q=пусто'
```

```bash
curl -sG http://127.0.0.1:8765/suggest --data-urlencode 'q=команда'
```

```bash
curl -s http://127.0.0.1:8765/recommend -H 'Content-Type: application/json' \
  -d '{"generation":"mock-generation-1","categories":["team"],"viewed":["course:mock-team"]}'
```

```bash
curl -s http://127.0.0.1:8765/development-plan -H 'Content-Type: application/json' \
  -d '{"generation":"mock-generation-1","categories":["team"],"viewed":[],"completed":["course:mock-team"]}'
```

Если в плане передать пустые `viewed` и `completed`, мок вернёт `needs_activity`. Несуществующий ID или устаревшее поколение приведут к 400. `completed` в действующем API принимает только ID курсов. Для поиска в мок-режиме уточнение можно отправить через `clarification_text` с исходным `q`.

**Ограничения мока:** это не полная реализация контракта и не модель. Он не вычисляет релевантность, не выдаёт настоящие токены уточнения, не симулирует реальные ограничения доступа, цены, генерацию каталога, все ошибки и порядок. Фиктивные `selection` / IDs нельзя использовать с реальным API. Для финансовых интерфейсов нужны отдельные согласованные примеры от бэкенда, а не выдуманные цены в этом стенде.

## 6. Подключение к настоящему прототипу

У владельца проекта, у которого уже установлены библиотеки и совместимые закрытые артефакты, из папки `05_code`:

```bash
PYTHONPATH=src HF_HUB_OFFLINE=1 .venv/bin/python -m alfa_reco serve --relevance --no-llm --port 8000
```

После загрузки модели: `http://127.0.0.1:8000/`, проверка состояния — `http://127.0.0.1:8000/health`, лаборатория — `/lab`. Эти локальные страницы есть в рабочей копии, но ранее были исключены из алгоритмической публикации; в публичном Git их может не быть. На другой машине самого кода недостаточно: нужны зависимости и совместимый комплект модели/каталога. Их передают отдельно разрешённым участникам, по инструкции для бэкенда; передача каталога фронтендеру для работы с моком не нужна.

Текущие пути и поля внутреннего API, ограничения на `selection_id`, уточнения и историю описаны в [передаче бэкенду](../05_code/docs/BACKEND_HANDOFF.md). При выборе подсказки передайте исходный `q` вместе с `selection_id` и `selection_generation`; для уточнения — исходный `q` и **либо** `clarification_token`, **либо** `clarification_text`, не вместе с выбором подсказки. Токен уточнения может устареть после перезапуска; повторите поиск. Сетевые вызовы и конечный контракт публичного API согласуются с бэкендером.

## 7. Что согласовать с бэкендером перед интеграцией

- URL и формат публичных методов, авторизацию и стандарт ошибок; прототип алгоритма не предоставляет пользовательскую авторизацию.
- Как получить актуальные название, ссылку, цену, валюту, возможность покупки и доступ именно этого пользователя; отдельно — курс и подписку.
- Как передаются факт покупки, прогресс и завершение, если нужен будущий маршрут. Текущий HTTP-план не умеет возобновлять начатый урок.
- Как показывать состояние отсутствия подходящего платного предложения и что делать при запросе бесплатного материала. В текущем алгоритме коммерческий paid-only режим ещё не включён.
- Какие события фиксируются: показ рекомендации с позицией, переход, подтверждённая покупка, начало/продолжение/завершение обучения и возврат. Кликом не подтверждается покупка; хранение и достоверность событий — ответственность бэкенда/аналитики.

Новые интерфейсы и события из этого списка — задачи для согласования, не готовые эндпоинты. До интеграции и проверки данных нельзя заявлять, что обновление уже увеличивает продажи или удержание.
