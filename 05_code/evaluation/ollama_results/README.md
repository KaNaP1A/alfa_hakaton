# Проверка локального извлечения Gemma

В [ollama_scenarios.json](../ollama_scenarios.json) — 30 вручную составленных сценариев: 12 коротких запросов, четыре с отрицанием, десять сложных, два с имитацией инструкций и два неоднозначных. Это небольшая проверка отдельных случаев, не слепая оценка и не доказательство покрытия всех пользовательских запросов. Фактические ответы и время каждого запроса — в [report.json](report.json). Команда запуска из `05_code`:

```bash
PYTHONPATH=src .venv/bin/python scripts/evaluate_ollama.py
```

На этой машине в выполненном прогоне 19 запросов дали хотя бы одно подтверждённое поле, восемь — ни одного, один завершился ошибкой, два пропущены маршрутизатором. Для 23 запросов заданы широкие ожидаемые основы предмета; модель извлекла такую основу в поле объекта в 11 случаях. Эта автоматическая сверка грубая: она может засчитать смысловую ошибку и не заменяет ручную оценку всех полей. Результат показывает, что Gemma 1B пока ненадёжна для обязательного извлечения информации.

Для 28 реально вызванных запросов медиана времени около 1,62 с, 95-й перцентиль около 2,87 с; один запрос завершился ошибкой спустя примерно 5,1 с. Время зависит от загрузки, прогрева, модели и оборудования. Приложение не вызывает Gemma на каждый ввод символа и сохраняет работоспособность поиска без неё. Все отрицания отдельно проверяются детерминированным правилом и блокируют LLM-бонус к score; полноценное исключение нежелательных объектов пока не реализовано.

При отдельной проверке API запрос «как удержать сотрудников а не клиентов» вернул на первых местах материалы про клиентов, хотя отрицание было обнаружено. Причина: исходный запрос, включая нежелательный объект, по-прежнему используется в базовом поиске. Это серьёзный открытый дефект качества; требуется разметить подобные запросы и реализовать проверенный учёт отрицаний до использования системы с реальными пользователями.
