# Передача рекомендательного алгоритма бэкенду

Документ фиксирует контракт локального прототипа, а не API промышленной платформы. Код находится в репозитории; модели и производные данные передаются отдельно. Рабочий профиль поиска — `relevance` (BM25 + E5 + CatBoost). Проведена частичная человеческая оценка синтетических диагностических запросов; независимого закрытого теста нет. Поиск не учитывает историю пользователя: рекомендации по истории и план — отдельные вызовы с эвристиками.

**Изменение контракта:** отдельный `mode=bm25` удалён и теперь возвращает HTTP 400. Клиентам, которые его передавали, нужно перейти на `mode=relevance`. Без выбора режима сервер также использует `relevance` и не переключается на BM25 при отсутствии модели. BM25 сохранён как компонент кандидатов и признаков внутри основного профиля. Код передаётся отдельно от комплекта модели; после обновления кода проверьте их вместе на целевом окружении. При изменении модели или каталога нужно подготовить новый комплект.

## Разделение ответственности

В текущей договорённости **бэкенд целиком отвечает** за авторизацию, актуальную публикацию, принадлежность материала каталогу сайта, права конкретного пользователя, ссылки, цены и их отображение. Алгоритм возвращает идентификаторы и рекомендации по снимку каталога; его `canonical_url`, `access_type` и `price` — сведения снимка, не авторизация и не подтверждение текущих условий.

Бэкенд проверяет все выдаваемые пользователю материалы и сопутствующие данные: основные результаты, альтернативы, подсказки о материалах, рекомендации, шаги плана и названия/ссылки в объяснениях. Он сопоставляет `entity_key` с собственной актуальной сущностью, исключает недоступные и неподтверждённые варианты, подставляет подтверждённые ссылки и цены. Неиспользуемые или неизвестные поля не выдаются пользователю. Если после проверки результатов мало, следует показать короткий список или отсутствие результата; не возвращать запрещённые материалы ради заполнения квоты.

**Ограничение интеграции:** действующий поиск не принимает список разрешённых пользователю ID, `recommend` и план тоже. Их внутренняя генерация не учитывает права пользователя. Проверка после вызова может уменьшить выдачу, а запрос большего `top` не гарантирует заполнения: у `/search` максимум 50 и есть собственные пороги, `/recommend` по HTTP возвращает до 5, план — до 3. При необходимости точной фильтрации до ранжирования и полноценных страниц понадобится расширить интерфейс алгоритма и переоценить качество; эта возможность здесь не реализована. Аналогично, отказ от одного шага может нарушить целостность плана: не утверждать, что оставшиеся шаги составляют исходный маршрут, без проверки на стороне бэкенда.

## Локальный запуск

Из `05_code`, с установленными зависимостями и подготовленным совместимым комплектом:

```sh
PYTHONPATH=src HF_HUB_OFFLINE=1 .venv/bin/python -m alfa_reco serve --relevance --no-llm --port 8000
```

Адрес `http://127.0.0.1:8000`. Для перенесённого комплекта вместо каталога по умолчанию добавить `--output /путь/к/комплекту/catalog`. Перед первым локальным запуском после переноса выполнить описанную ниже проверку и смену пути encoder. По умолчанию HTTP слушает loopback; это development-сервер. Для интеграции нужны отдельные доверенная сеть, аутентификация, ограничения запросов, мониторинг и контроль данных; бэкенд отвечает за их организацию. Контейнерный запуск предусмотрен в README, но фактически не проверен в Docker на текущей машине.

Пример клиента: [backend_client.py](../examples/backend_client.py). Он использует `http://127.0.0.1:8000`, по умолчанию отправляет `mode=relevance` и не реализует авторизацию или бизнес-валидацию. `/lab` — локальный интерфейс проверки, не контракт продукта.

## Метаданные каталога для бэкенда

В дополнение к комплекту модели можно отдельно подготовить снимок метаданных:

```sh
PYTHONPATH=src .venv/bin/python scripts/export_catalog_metadata.py \
  --catalog artifacts/catalog --output artifacts/backend_metadata_NEW
```

Папка назначения должна быть новой. В ней `materials.jsonl` содержит по одной JSON-строке на доступную поиску карточку; `manifest.json` — версию схемы (`schema_version: 1`), `generation`, SHA-256 каталога и файла, количество и срезы по типам. Скрипт сверяет каталог и источник по хешам и проверяет происхождение названий, описаний, аудитории и фасетов. При найденных расхождениях экспорт останавливается.

Основные поля строки: `entity_key`, `kind`, `source_id`, `title`, `description`, массивы `topics`, `tags`, `industries`, `target_audience`, `publication_status_snapshot`, `access_type_snapshot`, `data_quality_flags` и `provenance`. `entity_key` — ключ для сопоставления с результатами поиска; использовать снимок той же `generation`, что и ответ алгоритма. Пустые массивы и строки означают отсутствие значения в подготовленном снимке; они не подтверждают отсутствия данных на платформе. Происхождение незаполненного поля задаётся `null`, а непубличные темы не экспортируются.

Это закрытые производные данные выгрузки, несмотря на отсутствие пользовательских записей и полных текстов. `materials.jsonl`, снимок каталога и модель не публикуются в Git; их передают разрешённым участникам отдельно защищённым способом. Текущие публикации, доступ, цены и ссылки бэкенд получает из доверенных актуальных источников; поля `*_snapshot` не являются проверкой прав. Полная работа рекомендаций по-прежнему требует комплекта модели и каталога, описанного ниже: экспорт метаданных его не заменяет.

## HTTP-контракт

Расширенный профиль (цель, стадия, опыт, отрасль, формат и события) пока доступен как Python-интерфейс; существующий HTTP-контракт не изменён. Схема, примеры вызова, неопределённости и правила передачи уточнений описаны в [профиле и истории](PROFILE_HISTORY_2026-11-13.md). Интеграция этого интерфейса и проверка прав остаются на стороне бэкенда.

Для нового пользователя без истории подготовлен [алгоритм холодного старта](COLD_START_2026-11-13.md): `recommend_for_profile` возвращает необязательный вопрос `onboarding`, в том числе вместе с готовой выдачей; после выбора категории там доступны варианты `focus_facet` из текущего каталога. Необязательное поле `region` используется только для непроверенных подсказок о возможном упоминании города в заголовке. Их статусы и `verified: false` доступны в `profile_evidence.geography`, это не территориальные права или доказанная область применения. Существующий `/recommend` с категорией и пустым `viewed` использует новый порядок, но по-прежнему возвращает только список, без `onboarding`, и не принимает новые поля профиля. Возможные дубли перечислены в `profile_evidence.possible_duplicate_entity_keys` и обычно не скрываются; сворачиваются только при наличии совпавшего вручную подтверждённого URL и совпадении текста. Это не подтверждение одинакового доступа; проверка всех ID и прав остаётся на стороне бэкенда.

Все текстовые данные — UTF-8, POST — `Content-Type: application/json`. Идентификатор материала имеет вид `kind:source_id`, например `course:<id>`; IDs ниже условные. В профилях передаются только IDs из активного поколения, не персональные данные. `generation` берётся из `/health`. Все ответы зависят от версии каталога; не смешивать IDs и уточнения разных поколений.

Для поиска добавлены [правила разбора запроса](QUERY_UNDERSTANDING_2026-11-13.md): `request_understanding` содержит распознанный тип, отдельные действия и неподтверждённую аудиторию; `query_rules.unsupported_constraints` перечисляет условия, которые не гарантируются. Запрошенный тип может привести к пустой выдаче. При неопределённости `clarification` может содержать пустой список `options` и `allow_text: true`: ответ пользователя передаётся в `clarification_text`. Если пользователь выбрал конкретный материал или передал тип, противоречащий тексту, сохраняется явный выбор и показывается конфликт; материал, противоречащий одновременно переданному `kind`, вызывает ошибку. Это изменение алгоритмической политики; код следует обновлять вместе с инструкцией.

Для отдельных запросов об удержании сотрудников допускается слабое совпадение от 0,80 при дополнительных текстовых признаках. Такие карточки отмечены `support.weak_intent_match`, а ответ — `confidence.reason: weak_intent_match`, если нет более приоритетного предупреждения. Это не доказанная релевантность. Основной порог модели остаётся 0,84; он передаётся в `confidence.semantic_min`. Поле `support.unexpanded_card_coverage` отдельно показывает покрытие исходной положительной формулировки. `retrieval_diagnostics` отражает число кандидатов, рассмотренных и отклонённых материалов; в Python-профиле оно доступно внутри `goal_search`.

| Маршрут | Вход | Существенные поля ответа |
|---|---|---|
| `GET /health` | Без параметров | `status`, `generation`, `default_search_mode`, `relevance_available`, количество карточек; наличие указателя не заменяет пробный поиск |
| `GET /suggest` | `q` до 300 символов; `limit` 1–10, по умолчанию 6 | `generation`, `status`, `completions`, `related_topics`; у варианта `selection.id` и `selection.generation` |
| `GET /search` | `q` — непустой запрос до 300 символов; `mode=relevance`; `top` 1–50, по умолчанию 5; необязательный `kind` | `generation`, `query`, `results`, `alternatives`, `clarification`, `confidence`, `query_rules`, `request_understanding`, `retrieval_diagnostics` |
| `POST /recommend` | JSON ровно из `generation`, `categories`, `viewed` | `generation`, `results`; до 5 результатов, возможен пустой список |
| `POST /development-plan` | JSON ровно из `generation`, `categories`, `viewed`, `completed` | `generation`, `method`, `status`, `notice`, до трёх `steps` |
| `GET /catalog` | `q`, `kind`, `limit` 1–50 | `generation`, `items`; поиск по фрагменту названия, не проверка актуальных прав |

Типы `kind`: `article`, `course`, `document`, `podcast`, `webinar`, `calculator`. Подсказка передаётся в поиск как пара `selection_id` и `selection_generation`. Уточнение — либо `clarification_token`, либо `clarification_text` (непустой, до 100 символов); их нельзя сочетать друг с другом или с выбранной подсказкой. Токен подписан случайным ключом процесса и привязан к исходному запросу и поколению: после перезапуска или смены процесса поиск и выбор нужно повторить.

`categories`: `business`, `finance`, `team`, `marketing`, `technology`, максимум 5 значений. `viewed` — IDs просмотренных/отмеченных материалов, в порядке от более старых к более новым; максимум 50. Для плана `completed` содержит только ID курсов, максимум 50 уникальных материалов суммарно с `viewed`. Сервер проверяет принадлежность ID снимку и тип завершённого материала, но не факт просмотра/завершения, покупки или освоения навыка. Результат с пустой историей может быть пустым.

Пример профиля для `/development-plan` (ID и generation условные; для запуска подставить значения из текущего каталога):

```json
{"generation":"generation-...", "categories":["team"], "viewed":["article:..."], "completed":["course:..."]}
```

Статусы плана: `needs_activity`, `insufficient_evidence`, `partial`, `ready`. Шаги содержат `number`, `title`, `material`, `why`, `action`, `order_reason`, `evidence`. Порядок основан на эвристике сходства, а не проверенном графе навыков. Объяснения могут содержать названия исходных материалов истории и тоже требуют проверки перед показом.

В результатах поиска `entity_key`, `kind`, `title` — идентификация и данные снимка; `support`, `evidence`, `scores`, `ranking_override` — диагностика. `results` и `alternatives` уже упорядочены. `scores.final_score` не вероятность и не универсальная шкала; нельзя переупорядочивать ответ по нему, поскольку явный выбор и другие правила могут иметь приоритет. Пустые результаты и альтернативы — штатный ответ. Полный список фактических полей определяется действующим кодом [search.py](../src/alfa_reco/search.py), [server.py](../src/alfa_reco/server.py) и [development_plan.py](../src/alfa_reco/development_plan.py); новые поля не следует считать стабильными без совместного версионирования.

Ошибки проверки входа и устаревшей генерации — HTTP 400; неизвестный маршрут — 404; неверные локальные Host/Origin — 403; непредвиденные ошибки поиска — 500. Клиент должен обрабатывать таймауты и сетевые ошибки. Варианты и уточнения не следует использовать после смены поколения или перезапуска процесса.

## Комплект алгоритма и его перенос

Для создания отдельного минимального комплекта из активной совместимой версии:

```sh
PYTHONPATH=src HF_HUB_OFFLINE=1 .venv/bin/python scripts/prepare_backend_bundle.py --output artifacts/backend_handoff_NEW
```

Папка назначения не должна существовать. В ней `catalog/CURRENT.json`, активное поколение с `catalog.json`, `manifest.json`, `suggestions.json`, указатель и файлы relevance (`manifest.json`, `ranker.cbm`, `vectors.npz`, `normalized_catalog.json`), а также `encoder/` и `handoff_manifest.json` с контрольными суммами и версиями установленного окружения. `source.sqlite`, дамп и другие поколения не копируются. Каталог и нормализованные данные содержат производные материалы исходной выгрузки: **комплект закрытый, не публиковать и передавать только разрешённым получателям защищённым способом**. Отсутствие базы в комплекте не означает, что остальные данные общедоступны.

После копирования на целевой компьютер из `05_code` с установленными зависимостями:

```sh
PYTHONPATH=src .venv/bin/python scripts/prepare_backend_bundle.py --verify /путь/к/комплекту
PYTHONPATH=src .venv/bin/python scripts/prepare_backend_bundle.py --relocate /путь/к/комплекту
PYTHONPATH=src HF_HUB_OFFLINE=1 .venv/bin/python -m alfa_reco serve --output /путь/к/комплекту/catalog --relevance --no-llm --port 8000
```

`--relocate` сначала проверяет суммы и отпечаток encoder, затем меняет абсолютный `encoder_path` в **копии** манифеста и обновляет суммы комплекта. Хеши не являются электронной подписью: их нужно получать и сверять через доверенный канал. Не смешивать модель, каталог и векторы разных поколений. В комплекте нет исходного кода: его и закреплённые верхнеуровневые зависимости берут из этой версии репозитория. Python 3.11+; проверенные фактические версии Python и библиотек указаны в `handoff_manifest.json`, а прямые зависимости — в `requirements-relevance.txt` и включённых файлах. Полного переносимого lock-файла транзитивных зависимостей нет.

После запуска обязательно выполнить `/health`, реальный поиск, `/recommend` и `/development-plan`. Перенос на иной ОС/архитектуру и реальные интеграционные условия должны быть дополнительно проверены на целевой инфраструктуре; локальный тест этого не гарантирует.
