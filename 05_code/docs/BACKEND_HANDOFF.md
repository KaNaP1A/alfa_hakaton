# Передача поиска и рекомендаций разработчику бэкенда

## Что уже есть

Основной поиск — профиль `relevance`: BM25 и E5 подбирают кандидатов, CatBoost ранжирует пары «запрос — материал», затем работают правила допуска, уточнения и обработки явного выбора. Для поиска не нужен Ollama. `final_score` — внутренняя оценка модели, а не вероятность и не процент. Правила и явный выбор могут менять итоговый порядок, поэтому нельзя самостоятельно сортировать ответ по одному числу. Реальная человеческая оценка качества пока не проведена.

Персональные рекомендации по просмотрам реализованы отдельно в `src/alfa_reco/personalization.py`: это эвристика, использующая категории, просмотры и, когда доступно, векторы карточек. Они не обучены на истории реальных пользователей. Историю пользователей, авторизацию и права доступа должен хранить и проверять бэкенд сайта.

## Что брать в работу

1. Для локальной интеграции используйте существующий сервер `src/alfa_reco/server.py` и пример клиента [`examples/backend_client.py`](../examples/backend_client.py). Демо запускается через `Запустить ML демо.command`; CLI и зависимости описаны в [README](../README.md). Явно передавайте `mode=relevance` при поиске. Путь `/lab` — лаборатория, а не API продукта.
2. При старте проверяйте `/health` и действительно пробуйте поиск: `relevance_available` показывает наличие указателя артефактов и само по себе не доказывает успешную загрузку модели. Все артефакты одного каталога и модели должны соответствовать друг другу.
3. При вводе отправляйте `GET /suggest?q=...&limit=6`. Для выбора подсказки передайте в `/search` полученные `selection_id` и `selection_generation` как пару. Не подменяйте исходный текст запроса молча.
4. Поиск: `GET /search?q=...&mode=relevance&top=5`; опционально `kind`. Передавайте клиенту выданные результаты, близкие темы и уточнения в исходном порядке. Для выбора уточнения повторите поиск с тем же `q` и `clarification_token`, либо с `clarification_text`; варианты взаимоисключающие.
5. После просмотра материала сохраняйте событие на стороне сайта. Для рекомендаций передайте `POST /recommend` с JSON `{"generation":"...", "categories":[...], "viewed":[...]}`: `generation` из текущего ответа API, категории и идентификаторы просмотренных материалов в формате, возвращаемом каталогом (`entity_key`). Допустимые категории: `business`, `finance`, `team`, `marketing`, `technology`; не более 50 просмотров, более поздние элементы списка считаются более новыми. Подробные ограничения — в `personalization.py`. Сервер отклоняет устаревшую генерацию. Идентификаторы между разными версиями каталога необходимо перепроверять; не отправляйте персональные данные вместо идентификаторов.
6. Обрабатывайте ошибки 400/500 и таймауты, отображайте пустую выдачу и предлагаемые уточнения. Не считайте отсутствие результатов ошибкой модели или сервера.

Порт `59546` в примере соответствует текущему локальному запуску и может измениться: демо использует автоматически выбранный свободный порт. При интеграции передавайте актуальный внутренний адрес явно.

Пример:

```python
from examples.backend_client import RecommendationClient

client = RecommendationClient("http://127.0.0.1:59546")  # актуальный порт сервиса
health = client.health()
suggestions = client.suggest("как открыть кафе")
search = client.search("как открыть кафе")
recommendations = client.recommend(health["generation"], ["business"], [])
```

Подробности формата — в `server.py`, `search.py`, `suggestions.py` и `personalization.py`: это действующий контракт прототипа, его стоит зафиксировать в OpenAPI и покрыть контрактными тестами до интеграции с фронтендом.

## Артефакты и развёртывание

Git содержит код, но `.gitignore` исключает `artifacts/`, локальное окружение, дампы и базы. Поэтому одного клонирования недостаточно: ответственным лицам отдельно и безопасно передаются каталог с указателем `artifacts/catalog/CURRENT.json`, вся соответствующая версия каталога и её папка `relevance/`, а также модель E5 из `artifacts/models/multilingual-e5-small`. Состав и версии зависят от активных `CURRENT.json` и `manifest.json`; нужны `vectors.npz`, `normalized_catalog.json`, `ranker.cbm`, индекс подсказок и остальные файлы активных поколений. Файл `manifest.json` содержит абсолютный `encoder_path`: при переносе необходимо указать новый путь к той же модели и проверить её отпечаток, после чего проверить поиск. Не смешивайте индекс и веса от разных версий; при смене E5 нужно заново построить индекс и обучить CatBoost на новых признаках. Веса и каталог не помещайте в публичное хранилище без проверки прав на данные.

Текущий HTTP-сервер слушает только `127.0.0.1`, предназначен для локальной разработки и проверяет Host/Origin. Для продакшена нужен защищённый внутренний сервис или встроенный Python-адаптер с аутентификацией, ограничениями запросов, наблюдаемостью и контролем доступа на стороне сайта. Не открывайте демо-сервер напрямую в интернет. Передавайте запросы только из доверенной среды и решите, как защищать пользовательские данные в журналах.

Уточнения подписываются случайным секретом конкретного процесса и привязаны к тексту запроса и генерации. После перезапуска или при переключении на другой процесс токен может устареть. Для нескольких процессов потребуется спроектировать общий защищённый ключ и управление версиями либо направлять связанные запросы в тот же процесс; текущая реализация общего ключа не предоставляет. При ошибке предложите пользователю повторить поиск.

Перед промышленным запуском нужны отдельные человечески размеченные поисковые запросы и оценка качества и задержек на целевой инфраструктуре. Синтетические результаты не являются оценкой качества на реальных пользователях.

Экспериментальная дообученная E5 лежит отдельно и в рабочий поиск не включена: [метод и результаты](E5_FINETUNING_2026-11-12.md).
