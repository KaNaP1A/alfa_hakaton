# План развития по истории

Алгоритм возвращает до трёх следующих материалов с объяснением каждого шага. Просмотр части курса (например, нескольких лекций) и явная отметка о завершении всего курса — разные сигналы. Просмотр вебинара или другого материала тоже может стать основанием. Реальные действия из исходной базы автоматически не привязываются к посетителю: переданные отметки не являются проверенным прогрессом LMS.

План строится по содержанию каталога: E5, пересечению предметных слов и тем/тегов. Завершение курса весит сильнее простого просмотра. Кандидат обязан иметь связь с одним из материалов истории; выбранные интересы только уточняют порядок. Просмотренные и завершённые материалы и варианты с тем же названием исключаются. Повторы действий не усиливают сигнал. Если обоснованных продолжений меньше трёх, выдаётся короткий план или сообщение о нехватке данных.

При наличии подходящего документа или калькулятора второй шаг может предлагать практическую работу. Каждый шаг содержит материал, причину выбора, источник из истории, совпавшие темы/теги, объяснение порядка и предложенное действие. Семантическая близость — эвристика, не доказательство педагогической полезности. У нас нет подтверждённого графа предпосылок, уровней сложности и освоенных навыков. Этот модуль не использует CatBoost для прогноза обучения и не гарантирует повышение уровня знаний.

## API для бэкенда

`POST /development-plan`, JSON:

```json
{"generation":"актуальное поколение из /health", "categories":["team"], "viewed":[], "completed":["course:идентификатор"]}
```

Допустимы только эти четыре поля. Максимум 50 уникальных материалов в общей истории; `completed` принимает только курсы текущего каталога. В `viewed` указывается ID курса, часть которого просмотрена, либо другой карточки. Это не идентификатор отдельного урока: подробные события уроков необходимо привязать к родительскому курсу в доверенном бэкенде LMS. Сервер проверяет принадлежность ID каталогу, но не подтверждает факт просмотра или завершения.

Ответ: `generation`, `method`, `status`, `notice`, `steps`. Статусы: `needs_activity`, `insufficient_evidence`, `partial`, `ready`. У шага есть `number`, `title`, `material`, `why`, `action`, `order_reason`, `evidence`. Ошибки формата, ID и устаревшей генерации возвращаются как HTTP 400. Действующий `/recommend` сохраняет прежний контракт.

Алгоритм: максимум 20 последних уникальных источников истории (завершённые курсы имеют приоритет); до 20 кандидатов на источник. Вклад кандидата — `(3 для завершения / 1 для просмотра) / (1 + 0.15 × позиция источника) / позиция кандидата`. Совпадение с выбранной категорией умножает сумму на 1.15. Для практического второго шага допускается кандидат с оценкой не ниже 60% текущего лидера. Эти коэффициенты инженерные, не обучены и не названы оптимальными. Порядок элементов истории служит приблизительным порядком давности; датами он не считается.

Перед промышленным использованием нужны оценка планов людьми, реальные события с авторизацией и эксперименты по полезности следующего шага. Автотесты проверяют контракты, объяснения и исключения, а не эффективность обучения.


Дополнительный контроль тематической связи: общие слова «шаг», «модель» и подобные исключаются. При наличии E5 требуется косинусная близость ≥0.78 вместе с лексическим подтверждением, либо ≥0.84 с общими темами/тегами, либо ≥0.90. Без E5 нужно лексическое подтверждение. Эти пороги также эвристические.

Пример клиента для `/development-plan` добавлен в `examples/backend_client.py`. Хранение и отображение профиля и плана организует интегрирующая команда.
