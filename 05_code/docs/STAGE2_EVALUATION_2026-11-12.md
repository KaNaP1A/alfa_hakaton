# Второй этап: подготовка человеческой оценки

## Что подготовлено

Пул `artifacts/annotation_pool/current_diagnostic_20261112` строится на текущем поколении каталога и одной версии кода с реальным вызовом `SearchEngine.search`. Для каждого из 75 ранее подготовленных запросов собраны выдачи BM25, текущего E5-профиля с отключённым CatBoost и рабочего E5 + CatBoost. Последние два сравниваются с одинаковой канонизацией, кандидатным пулом и правилами допуска. BM25 использует свои правила обработки; это сравнение профилей, а не отдельного вклада одного компонента. В пул дополнительно входят альтернативы и до трёх случайных карточек; их релевантность не назначается автоматически.

Запросы составлены ассистентом и уже были видны при разработке. Все строки обозначены `validation` для диагностического расчёта; это **не новый закрытый тест и не независимая выборка пользовательских запросов**. Все оценки изначально пустые. Два человека могут оценить кандидатов независимо и вслепую к методам; это не сделает сами запросы независимыми. Для окончательного подтверждения улучшений позже необходим новый набор задач и семей, полученный независимо и не использованный при разработке, с отдельной разметкой и фиксацией до подбора.

В `manifest.json` сохранены хеши каталога, модели, скрипта, исходных запросов и Python-кода, а также хеши пула, ранжирований и пустых оценок. Папка находится в `artifacts/`, не включена в Git и содержит производные материалы закрытой выгрузки: передавать только разрешённым лицам защищённым способом. Файлы `rankings.jsonl` и `diagnostics.jsonl` не показывать оценщикам до завершения независимой разметки. Для каждого оценщика подготовлен отдельный `reviewer_a/review.csv` и `reviewer_b/review.csv`; там нет данных о методах и позициях. Данные из CSV можно открыть в табличном редакторе; длинные описания могут требовать увеличения ширины ячейки. Оценщики не должны просматривать оценки друг друга.

Для Excel с русскими региональными настройками созданы отдельные копии `reviewer_a/review_excel.csv` и `reviewer_b/review_excel.csv`: они содержат те же 827 пар и используют разделитель `;` с указанием `sep=;`. Исходные `review.csv` не менялись. Если Excel всё равно показывает одну колонку, импортируйте файл через «Данные → Из текста/CSV», выбрав UTF-8 и разделитель «точка с запятой». Сохраните результат в CSV UTF-8; импортёр принимает и запятую, и точку с запятой. Если в исходном `review.csv` есть несохранённые оценки, они не переносятся автоматически в новую копию.

Если Excel неправильно распознаёт кодировку CSV, используйте готовые книги `artifacts/outputs/01a1d155-2b9e-7363-83ba-5a30aa40ec49/reviewer_a.xlsx` и `reviewer_b.xlsx`: русский текст сохранён в формате Excel, столбец `grade` расположен первым. Заполняйте только жёлтый столбец, сохраняйте в `.xlsx` и не изменяйте ID. Импортёр ниже принимает `.xlsx` непосредственно, без экспорта в CSV. Новые книги содержат оценки из сохранённого исходного `review.csv`, но не несохранённые изменения, которые открыты в Excel.

## Инструкция оценщикам

Сопоставьте каждую карточку с полным текстом задачи и её ограничениями. Оценивайте только доступные название и описание: они могут быть недостаточны для проверки полного содержания. Не считайте цену, уровень, время или права известными, если они не подтверждены. Отрицания, желаемый формат, субъект и действие нужно учитывать, а не ориентироваться только на общие слова.

- `3` — материал непосредственно помогает выполнить основную задачу.
- `2` — частично помогает, но не покрывает важную часть задачи.
- `1` — связан с темой, но основную задачу почти не решает.
- `0` — не подходит или противоречит задаче.
- Пустое поле — нельзя уверенно оценить по имеющимся данным. Это **не ноль**.

В своём файле заполняйте только колонку `grade`, целым числом 0–3 или оставляйте пустым. Не изменяйте ID и не удаляйте строки. Не используйте автоматические подсказки/разметку и не смотрите выдачи методов. Для достоверности два оценщика работают независимо; расхождения разрешаются отдельным согласованием. Порядок карточек перемешан, но сам факт независимости людей организационный процесс, программа его подтвердить не может.

## Импорт оценок и расчёт

Из `05_code`, после возвращения двух отдельно заполненных CSV:

```sh
PYTHONPATH=src .venv/bin/python scripts/import_review_csv.py artifacts/annotation_pool/current_diagnostic_20261112 \
  /path/to/reviewer_a.csv --reviewer reviewer_a --output artifacts/annotation_pool/current_diagnostic_20261112/reviewer_a.jsonl
PYTHONPATH=src .venv/bin/python scripts/import_review_csv.py artifacts/annotation_pool/current_diagnostic_20261112 \
  /path/to/reviewer_b.csv --reviewer reviewer_b --output artifacts/annotation_pool/current_diagnostic_20261112/reviewer_b.jsonl
PYTHONPATH=src .venv/bin/python scripts/merge_reviews.py \
  artifacts/annotation_pool/current_diagnostic_20261112/reviewer_a.jsonl \
  artifacts/annotation_pool/current_diagnostic_20261112/reviewer_b.jsonl \
  --output artifacts/annotation_pool/current_diagnostic_20261112/judgments_merged.jsonl
PYTHONPATH=src .venv/bin/python scripts/evaluate_annotation_pool.py \
  artifacts/annotation_pool/current_diagnostic_20261112 \
  --judgments artifacts/annotation_pool/current_diagnostic_20261112/judgments_merged.jsonl \
  --output artifacts/annotation_pool/current_diagnostic_20261112/human_metrics.json
```

Выходные имена должны быть новыми; исходный пул не перезаписывается. Импорт проверяет хеш пула, допустимые оценки, дубли и полный список пар. Оценки при несовпадении остаются неразрешёнными до заполнения `adjudicated` в объединённой копии; пустое не превращается в отрицательную метку. Только полностью оценённые запросы попадают в расчёт family-macro NDCG@5, MRR@5 и P@5. Из-за исключения неполных задач возможен сдвиг; выводятся количество завершённых задач и оценки. Идеальный порядок строится только по кандидатному пулу, а не по всему каталогу. Три случайные карточки не обеспечивают полноту recall; отсутствие хороших кандидатов не доказывает отсутствия материала в каталоге.

## Что ещё необходимо

1. Провести независимую человеческую разметку и разрешить разногласия. До этого оценок и достоверных метрик нет.
2. Отдельно подготовить независимо сформулированные свежие семейства запросов, заранее отделить validation и закрытый test. Настройка, выбор признаков и решений должны использовать только training/validation; test проверяется после фиксации модели и политики. Разделение должно проверять близкие формулировки и контрасты, а не только ID.
3. Сформировать отдельный размеченный набор отсутствующих ответов и имеющихся ответов с экспертной проверкой каталога; измерить ошибочные выдачи и необоснованные отказы. Предложенный диагностический пул сам по себе их не устанавливает.
4. Подготовить и разметить сценарии персонализации: одинаковые задачи для разных стадий, сфер, опыта и истории, включая пустую историю и маршруты. Текущий search API профиль не принимает, поэтому сейчас не заявляется, что качество персонализации оценено.
5. Добавить парные интервалы по семействам и срезы, а также контроль времени и доли полностью размеченных кандидатов для финального теста. Офлайн-релевантность не измеряет покупки или конверсию.
